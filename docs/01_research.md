# День 1 — Research: digital business lending

## Цель
Определить минимальный пользовательский путь для MVP кредитования бизнеса и требования к данным/экранам.

## 1. Точка
Наблюдения по публичному пользовательскому пути:
- предварительное решение можно получить по ИНН и телефону/имени руководителя;
- после предварительного решения пользователь заполняет расширенную анкету;
- используются данные об оборотах и документы;
- одна заявка может приводить к нескольким вариантам финансирования;
- акцент на онлайн-процессе и минимуме визитов/формальностей;
- в качестве ключевых факторов публично названы обороты и отсутствие проблем с предыдущими займами.

**Вывод для MVP:** первым шагом запрашивать ИНН + продукт + сумму/срок, затем автоматически показывать данные компании и запрашивать только недостающие поля.

## 2. Т-Банк
Наблюдения:
- онлайн-подача заявки;
- решение может формироваться по ИНН, анкете и информации об оборотах;
- для части продуктов документы не собираются на первом этапе;
- статус заявки доступен в личном кабинете;
- при необходимости банк может запросить дополнительные документы;
- есть разные продукты: кредит, овердрафт, инвестиционное/оборотное финансирование.

**Вывод для MVP:** статус заявки должен быть видимым в кабинете, а запрос дополнительных документов — отдельным состоянием, а не ошибкой процесса.

## 3. Сбер
Для MVP ориентируемся на общий паттерн digital SME lending: идентификация бизнеса, сбор финансовых данных, автоматическая проверка/скоринг, предложение условий, электронное оформление. Конкретные коммерческие условия Сбера не копируем в MVP: они нужны только как benchmark.

## 4. Общие паттерны
| Наблюдение | Решение MVP |
|---|---|
| ИНН — основной идентификатор бизнеса | ИНН вводится первым |
| Много данных уже существует во внешних источниках | Автозаполнение из моков |
| Предварительное решение отделено от полного оформления | Разделяем проверки/скоринг/решение |
| Документы нужны не всегда | Состояние «Нужны документы» |
| Несколько продуктов могут быть релевантны | Каталог + единый мастер заявки |
| Клиенту важна прозрачность | Timeline статусов + причины решения |
| Банку нужен ручной контроль исключений | Кабинет банкира со спорными заявками |
