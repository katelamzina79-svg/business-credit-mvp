# День 3 — Катя: клиентский интерфейс и демонстрационный сценарий

## Что готово в этой версии

- Стартовая страница с входом через существующий API авторизации.
- Кабинет клиента: счётчики заявок, каталог из трёх продуктов и форма заявки.
- Проверка ИНН по мок-реестру и автозаполнение карточки компании.
- Создание черновика через API и отправка заявки отдельным действием.
- Карточки заявок с суммой, сроком, продуктом, статусом и индикатором этапа.
- Просмотр истории статусов по каждой заявке.
- Состояния пустого списка, ошибок, загрузки и повторного обновления.

## Файлы

- `backend/templates/list.html` — клиентский интерфейс.
- `backend/templates/layout.html` — общий layout и подключение Tailwind/HTMX.
- `backend/app/main.py` — маршрут `/` уже открывает этот интерфейс.

## Проверка руками

1. Из корня репозитория: `cd backend && docker compose up --build`.
2. Открыть `http://localhost:8000/`.
3. Войти `client@example.com` / `client123`.
4. Ввести ИНН `7701234567` и нажать «Проверить».
5. Выбрать продукт, сумму, срок и цель; нажать «Создать заявку».
6. Убедиться, что заявка появляется в списке со статусом «Отправлена».
7. Раскрыть «История статусов» и проверить, что видны создание и отправка.

Второй тестовый ИНН: `7707654321` (у него в мок-данных 45 дней просрочки; интерфейс не делает вывод о решении на основании одного поля).

## Что сказать жюри

«Мы не просто собираем анкету: компания находится по ИНН, пользователь видит, какие данные подтянулись, отправляет заявку и затем отслеживает этап обработки. Решение отделено от факта отправки — создание заявки не обещает одобрение».

## Ограничения, которые нельзя скрывать

- Это демонстрационный стенд с синтетическими данными, не банковская система.
- ИНН ищется в локальном мок-реестре, внешнего подключения к ЕГРЮЛ пока нет.
- Токен в интерфейсе хранится в `sessionStorage`; это приемлемо только для локального MVP, не для промышленной системы.
- Клиентский интерфейс готов; полноценный интерфейс сотрудника банка — отдельная следующая задача.
